## Guide

### Foundations and data structures

Begin with authority-bearing state before following any dash control flow. Read ordered movement settings, timer state, and tick-width propagation as one foundation: server-resolved values must survive every DTO and cache without truncation, stale overwrite, or paused wall-time leakage. Later planning and reconciliation assume these invariants rather than defending against malformed state again.

#### Make movement settings an ordered authority snapshot

`MovementSettings` stops being a loose bag of locally overwritten values. It now stores the server-resolved dash distance and duration and delegates effective speed updates to a small ordered state. Invalid values and observations older than the latest server tick are rejected; resetting the state explicitly starts a new session in which lower tick numbers are valid again.

This removes the need to reproduce backend buff arithmetic in Unity. The server sends the effective result, and the client preserves only ordering and validity invariants needed for prediction.

#### Carry long-lived ticks and pause-aware dash time

The prediction service widens snapshot ticks to `ulong`, receives the scoped server clock, removes hard-coded dash fallbacks, and replaces a raw `Time.time` origin with `PauseAwareElapsedTimer`. The timer shifts its effective start forward on resume, so paused wall time never advances the local dash curve.

Tick width changes propagate through player snapshots, delta caches, remote interpolation samples, and player entities. This is a protocol migration rather than a numeric precision tweak: every storage and method boundary must agree or ordering will truncate at one seam.

### APIs and entrypoints

Follow the three ways authoritative movement data enters the client: applying a settings snapshot, receiving repeated persona-scoped parameter events, and initializing speed during player spawn. The reading order shows that all paths converge on the same ordered state instead of writing public fields independently. Notice where a new session explicitly resets ordering and where optional dash values preserve the last valid observation.

#### Commit speed, timing, and dash values as one snapshot

`ApplyServerParameters` routes effective speed through the ordered state before updating input thresholds and fixed-step timing. Positive dash values replace the current prediction parameters; absent or invalid optional values leave the last accepted authority intact. The public effective-speed method returns whether an observation was accepted, while the reset method deliberately clears tick ordering at the session boundary.

### Core behavior

Read the dash as an authority pipeline rather than one method: shared planning chooses the unconstrained trajectory, Unity resolves scene collisions, shared sampling advances presentation, and server events terminate or reconcile the action. Then review deletion of client-side speed composition as part of the same boundary cleanup. The central invariant is that deterministic gameplay math belongs to the shared package while Unity owns only engine-specific collision and visual application.

#### Plan a dash from prediction state, then resolve Unity collisions

Prediction now waits until positive server-resolved distance and duration are available. Shared `DashKinematics.Plan` chooses direction and raw target from the predicted/physics position, current velocity, aim direction, and authoritative distance. Unity then owns the environment-specific collision query that shortens the raw target against scene geometry.

This boundary is deliberate: direction and unconstrained displacement must match backend math exactly, while collider casts cannot live in the platform-neutral gameplay package. Starting from prediction state rather than the smoothed render transform also avoids baking presentation lag into the simulated target.

#### Reconcile authoritative dash events without stealing lifecycle ownership

An authoritative dash event first refreshes settings. If local prediction never started, the event can bootstrap the presentation from the current predicted position; if prediction is already running, it retargets the remaining path and restarts timing with only the remaining duration. In both paths, a server-provided collision-resolved target wins over the local estimate.

The client is allowed to predict the curve, but it does not declare the gameplay action finished. Completion and rejection events remain the authority that stop prediction and reconcile the final position.

#### Sample the shared curve and hold its exact endpoint

Each frame asks `DashKinematics.Sample` for the current XZ position using pause-aware elapsed time. Unity applies that sample through its physics controller, including the exact completed endpoint. Once the shared sample reports complete, the animation state freezes there but `_isPredictingDash` remains true until the server sends its lifecycle event.

That distinction prevents two failure modes: a local lerp drifting from backend easing, and an animation timeout being mistaken for authoritative gameplay completion.

### Integration and wiring

After understanding the pure path, trace lifecycle signals that keep it coherent across player replacement, pause, resume, snapshots, and RTT updates. Read local timer resets before controller subscriptions and boundary gating. What matters is that every transition updates shared temporal authority exactly once before clearing prediction buffers or advancing presentation.

#### Reset dash timing with player and pause lifecycle

The prediction service resets timer state when a player is attached, cleared, or a dash stops. Pause and resume callbacks freeze and restart the elapsed timer, while RTT initialization and smoothing feed the shared server clock. This keeps local dash animation and authoritative effect restoration on consistent latency and pause inputs without merging their separate clocks.

#### Gate typed phase events and observe every snapshot

The movement controller receives the scoped clock and passes it into prediction. Pause/resume subscriptions now require tick-bearing payloads. Each boundary is applied to the clock before local pause state and buffer resets; duplicate or out-of-order boundaries can therefore return without applying the visual transition twice. Every accepted position snapshot also advances the clock before it enters the presentation queue.

The same change removes the old speed-boost handler from subscribe, unsubscribe, pause, and cache paths. The large deletion is part of the authority transfer, not unrelated cleanup.

Use independent review when it materially increases confidence; do not request it merely because a turn is ending. During user iteration, prefer focused local checks and a reviewable preview. Request design review before consequential architecture or plans become expensive dependent implementation. Present constraints, credible alternatives, important assumptions, and validation strategy.

Use review_start with a short summary. Modes: Quick (medium effort) for bounded changes or checking fixes; Standard (high) for stable implementation checkpoints and consequential design choices; Deep (max) for high-impact/unresolved risks and mandatory final review. Read the review-workflow skill when more context is needed. Additional brief and evidence references are optional and disclosed lazily.

Before shipping or opening/updating a PR, complete a Deep IMPLEMENTATION review with scope:publication covering the exact published candidate and resolve blocking findings. A design review, Quick/Standard review, failed or incomplete run does not satisfy this requirement. Repeat Deep assessment after candidate changes; an existing result suffices when the scoped base/head candidate is unchanged. Descendant PR helpers can inherit a completed assessment for the same project, environment and unchanged candidate. Helpers forbidden to change branches must report blocking findings to the author, not rerun review or bypass the gate. Report meaningful limits rather than implying exhaustive safety.

In GitButler, target this workstream's checkpointed branch or explicit base/head. Never select HEAD, gitbutler/workspace, the entire working tree, or every applied branch. Checkpoint only owned/authorized files or hunks, preserving other agents' work. For iterative segment reviews, lower stack commits are dependency context. For ship/PR, use scope:publication: merge-base to the selected branch includes all its ancestors without other applied stacks. With explicit base/head, choose the full publication delta. Outside GitButler, also declare the destination branch in target.upstream (--upstream origin/main); base must be its merge base with head. Other workspace changes do not invalidate an unchanged target. The reviewer reads immutable commits without checking out or unapplying anything. Identify the source revision of tests/captures, especially combined-workspace evidence.

Prefer reuse:auto on the same workstream, including Deep follow-ups that verify fixes. Every new run must independently assess its pinned candidate at the selected effort; prior approval does not carry over. Use reuse:new for fresh judgment, a changed direction, or suspected anchoring. Identical completed requests may return their unchanged result; reuse:new forces a fresh assessment. Give the delta and finding IDs being addressed. Keep an active run's candidate fixed; submit later changes as a new run, never steer it onto changing files. Use review_result with the returned RUN ID (bounded wait up to 60s); do not use an old thread output as current clearance. Apply relevant agent instructions and principle leaf skills. Verify findings and finish authorized fixes.

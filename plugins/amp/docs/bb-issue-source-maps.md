# Custom ACP providers have no readable contract — `bb plugin new` sets the precedent

**Environment:** bb 0.35.1, macOS. Writing a plugin that registers [Amp](https://ampcode.com) as a custom ACP provider.

## Summary

`bb plugin new` already takes the position I'm arguing for. It writes a full, readable, commented copy of the host contract into every new plugin — `packages/templates/src/plugin-scaffold.ts:434`:

```js
await writeFile(join(typesDir, "bb-plugin-sdk.d.ts"), PLUGIN_SDK_DTS);
```

That's 12,740 lines with ~1,155 lines of comments, generated by `scripts/build-public-sdk-dts.mjs`, and it's genuinely excellent: I could write the whole backend of my plugin without opening bb's source once. The scaffold's clear premise is that a plugin author should be handed the contract, not made to infer it.

The gap is that this covers the **plugin API** — what you *call* on `BbPluginApi`. There is no equivalent for the **ACP agent contract** — what bb *reads back* from a provider's `session/new` response. Searching the scaffolded `.d.ts` for `thought_level` / `reasoningEffort` returns 4 incidental hits and nothing about model-catalog construction or label rendering.

That asymmetry looks structural rather than intentional: custom ACP agents aren't a plugin API at all, they're `customAcpAgents` in `~/.bb/config.json`, so they fall outside the artifact that would otherwise document them.

## What the documented path does and doesn't answer

`docs/configuration.md` covers registration properly — `customAcpAgents` keys, `modelCli`, `reasoningCli`, `nativeReasoning`, and the precedence between a protocol `thought_level` option and a declared launch spec. I built against it and it held up.

The questions it doesn't reach are all about what bb does with what the agent sends back:

- **Model labels.** Claude Code renders `Opus 5` with a dimmed `1M`. I wanted the same for Amp's underlying models. Labels turn out to be split on a trailing parenthesised group — a genuinely nice convention, and one I could only find by reading built UI code.
- **Reasoning labels.** Are they taken from the agent's `option.name`? No — they're looked up from a fixed table by level, and the agent's `name` is discarded.
- **Model descriptions.** A model config option's `description` is replaced with `""` during catalog construction, so it can't be surfaced.
- **Categories.** Which `category` values bb reads, and what each one drives in the UI.

None of these are unreasonable to leave undocumented. The problem is only what happens next.

## Why there's no fallback

When docs stop, the normal recourse is reading the code — and for this one contract, it isn't available. `bb-acp-bridge.mjs` ships minified with no source map, so the answers above came out of reading identifiers like `Fu`, `$f`, and `qu`.

That's an explicit opt-out, not a missing default. The shared helper defaults maps on — `scripts/build-utils.mjs:67`:

```js
export async function buildNodeEsmEntry({
  …
  sourcemap = true,
  target = "node22",
}) {
```

But the child bundles don't go through it. `apps/host-daemon/scripts/build-bundles.mjs` is a separate `esbuild.build()` over `bundleTargets` that turns them off (lines 33, 36):

```js
      minify: true,
      …
      sourcemap: false,
```

So every target in `apps/host-daemon/scripts/bundle-manifest.mjs` ships unmapped: `bb-acp-bridge.mjs`, `bb-claude-code-bridge.mjs`, `bb-pi-bridge.mjs`, `daemon-bundle.mjs`, `bb-parcel-watcher-child.mjs`, and the `bb` CLI itself. Packaging isn't the cause — `packages/bb-app/scripts/build.mjs` only copies each `apps/*/dist` wholesale.

Worth noting bb already gets this right on the plugin side: `packages/plugin-build/src/build-plugin-server.ts:145` sets `sourcemap: true`, so my plugin's own backend debugs cleanly. It's the host half of the same conversation that's opaque.

## Proposals

In order of preference.

1. **Extend the scaffold's premise to ACP providers.** A commented `.d.ts` (or a doc section) describing what bb reads from `session/new`: recognised `category` values, how `supportedReasoningEfforts` is derived, the trailing-parenthesis label convention, and which agent-supplied fields are dropped. Same principle as `PLUGIN_SDK_DTS`, applied to the one contract it doesn't cover.
2. **Ship source maps for the child bundles.** Set `sourcemap: true` in `apps/host-daemon/scripts/build-bundles.mjs`. esbuild emits maps happily alongside `minify: true`, and the `.map` files land in the same `dist/` that packaging already copies. `check-bundles.mjs` only sums and prints sizes — no budget to breach — though printed totals will move if `.map` files get counted. If artifact size is the concern, `sourcemap: "external"` keeps the bundles byte-identical.

(1) is the real fix; (2) is cheap and also buys readable stack traces in the processes that run third-party agents.

## Smaller, related

- `packages/plugin-build/src/build-plugin-app.ts` sets no `sourcemap`, so plugin *frontend* bundles are unmapped while their servers are mapped — same one-line shape, affects every plugin author with an `app.tsx`.
- `apps/app`'s Vite build has no `build.sourcemap`, so the SPA is unmapped as well. That's the framework default rather than an opt-out, and the artifacts are far larger, so I've left it out of the ask — though it is where the label and reasoning-picker behaviour above actually lives.

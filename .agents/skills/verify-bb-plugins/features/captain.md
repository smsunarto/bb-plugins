# Captain

Captain makes a bb thread a long-lived director: it starts a pinned Claude Code thread with its own Drive, rules and repos, and briefs crew threads on Tasks tasks. The user sees a Needs you banner above a Captain's composer, an Overview tab beside its thread (Needs you, Tasks, Routines, Drive), a Captain glyph and Needs you count on its sidebar row, `Adopt into Captain…` in every thread menu, a `New Captain directing <project>` button on GTD Sidebar project headers, and Crew models and Captain icons sections in its settings. Everything is also reachable through `bb captain …`.

## Sub-features

- `captain-new-cli` starts a Captain with `bb captain new`: a pinned thread titled with the name, in a shared `Captains` project, with empty `CAPTAIN.md`, `CREW.md` and `NOTES.md` in its Drive. A rerun with a live name converges it (`state: exists`) and starts no turn.
- `captain-new-sidebar` opens the `New Captain` dialog from a GTD Sidebar project header's `New Captain directing <project>` button, checks Name and Repos, shows Captain's refusals, and opens the started or converged Captain's thread.
- `captain-sidebar-lead` shows a Captain's own icon (default glyph, a bb icon name, or a picture) in place of the globe on its sidebar row, labelled `Captain`.
- `captain-sidebar-count` shows a Captain row's Needs you count, labelled `<n> needs you`.
- `captain-stays-open` shows Snooze and Settle disabled on a Captain's sidebar row and in its menu, with the reason `Captain threads stay open`.
- `captain-banner` renders the Needs you queue above a Captain's composer only: `All clear` with an `Overview` link when empty; one tab per item with a `<n> waiting` count, option buttons (the first marked recommended), `Later` (hide for an hour), `Other…`, and keys `1`–`9`, `Enter`, `L`, `S`.
- `captain-answer` answers an ask from the banner, the Overview, or `bb captain ask resolve`. The answer is recorded and sent to the Captain.
- `captain-overview` is the `Overview` panel tab, shown only on a live Captain's thread, with collapsible `Needs you`, `Tasks`, `Routines` and `Drive` sections whose collapsed state persists per thread.
- `captain-overview-default` lands the side panel on Overview when it is opened generically on a Captain thread.
- `captain-drive` lists Drive files as cards in Overview, opens one in a file preview, and reads and writes them with `bb captain drive read|write`.
- `captain-routines-ui` creates, edits, pauses, resumes, tests and deletes routines from Overview's Routines section.
- `captain-routines-cli` does the same with `bb captain routine add|list|show|update|pause|resume|run|remove`.
- `captain-adopt` brings an existing thread into a Captain's crew on a new or existing task from `Adopt into Captain…` in a thread menu.
- `captain-crew-models` edits each role's model ladder under **Settings → Plugins → Captain → Crew models**.
- `captain-icons` sets a Captain's sidebar icon by name or picture under **Captain icons**, or by name with `bb captain icon`.
- `captain-cli-ops` covers the rest of the CLI: `repo add|remove`, `status`, `dispatch` (with `--dry-run`), `verdict`, `tell`, `ask`, `archive`.
- `captain-archive` releases the crew and archives the Captain. Overview, the banner and the sidebar icon go away, and its routines pause.
- `captain-instructions` gives Captain threads `captain.md`, the Drive's `CAPTAIN.md` and the skills `captain-brief`, `captain-review-loop`, `captain-routines` and `captain-ship`. Crew threads get `crew.md`, their role contract and `CREW.md`, and Review crew also get `captain-review-lenses`. Captain registers no agent tools.
- `captain-background` runs the `check` service, which wakes a Captain once per crew thread stalled for 15 minutes, retries undelivered answers, and restarts a rate-limited crew thread on the next ladder rung. It also runs the `routines` maintenance service.
- `captain-live-notices` tells live threads when `CAPTAIN.md`, `CREW.md`, or a role file changes (a diff or the full text), attaches CREW.md rules a crew thread has not yet received to crew messages, and tells the Captain when no ladder rung is left. <!-- unverified: only the unseen-rules part was driven (stand-in) -->

## How to get to it (user POV)

- **Start a Captain:** run `bb captain new --name <name> --repo <project>`, or, with GTD Sidebar and two or more projects in view, choose `New Captain directing <project>` (the anchor glyph) on a project group header. Headless Chrome shows that button without hover.
- **A Captain's thread:** choose its sidebar row, which leads with the Captain glyph. The Needs you banner sits above the composer.
- **Overview:** choose `Overview` in the banner's `All clear` line, or the side panel's `Show overview panel` tab button (open the panel with bb's `Show right panel (Ctrl + \)` button in the thread header).
- **Adopt:** right-click any non-Captain thread row, or focus it and press `Shift+F10`, or open the thread header's `Thread actions` menu, then choose `Adopt into Captain…`. The item appears only while a live Captain exists.
- **Settings:** open **Settings → Plugins → Captain** (`/settings/plugins/captain`) for **Crew models** and **Captain icons**. Captain has no plugin settings schema: `"$TB" plugin config captain --json` prints `"schema": {}`.
- **CLI:** use `bb captain --help`, which lists `new`, `archive`, `repo add|remove`, `drive read|write`, `dispatch`, `verdict`, `tell`, `ask`, `ask resolve`, `ask show`, `status`, `routine add|list|show|update|pause|resume|run|remove` and `icon`. Every command takes `--json`. A success prints `{ ok, results: [{ id, ok, state, … }] }`, except `status`, which prints `{ ok, cursor, counts, rows }`. A refusal exits 1 and prints `{"ok":false,"error":{"code":"refused",…},"blockers":[{"reason","fix"}]}` on stdout and the same blockers as text on stderr. `routine fire` is left out of the list and only the automation calls it, though `routine fire --help` still prints.

## Driving it with agent-browser

Preconditions:

- The doctor passes with `--plugin captain --plugin scott-tasks --plugin gtd-sidebar`. Captain refuses `new` and `repo add` while Tasks (`scott-tasks`) does not answer, and refuses `routine add` while bb's built-in Automations does not answer. Without Push notifications, `new` prints a warning and continues. <!-- unverified: from source; these refusals need Tasks or Automations stopped -->
- **`bb captain new` itself is paid and writes the real home directory.** `new` (and the sidebar dialog's `Start Captain`, which runs the same server path) spawns the thread with provider `claude-code` and permission mode `full` fixed in code, sends its first message at once, runs `mkdir -p $HOME/Captains`, and makes the test `Captains` project point at it. A rerun that converges runs the same steps, so it is not free either. Never run `new` or a filled `Start Captain` in a verification run.
- **Use the seeded stand-in Captain instead (test only, not `bb captain new`).** It is a fake-provider thread registered straight into Captain's test database, so every turn sent to it is free. Steps marked **(stand-in)** were driven against it on bb 0.50.1. Register the fake agent first ([SKILL.md](../SKILL.md) **Free agent turns**), write `ready` into `$EV/reply.md`, then:

  ```bash
  FAKE=acp-verify-fake
  FX="$BB_THREAD_STORAGE/verify/$RUN-fixtures"; mkdir -p "$FX/Captains"
  for n in alpha beta; do git init -q "$FX/verify-$n" && git -C "$FX/verify-$n" commit -q --allow-empty -m init
    "$TB" project create --name "verify-$n" --root "$FX/verify-$n" --json | jq -r '.project.id // .id'; done   # <alpha-id>, <beta-id>
  "$TB" project create --name verify-Captains --root "$FX/Captains" --json | jq -r '.project.id // .id'   # <home-id>
  "$TB" thread spawn --project <alpha-id> --provider "$FAKE" --title "Alpha fixture one" --prompt hello --json | jq -r '.thread.id // .id'   # <alpha-one-id>
  "$TB" thread spawn --project <beta-id> --provider "$FAKE" --title "Beta fixture one" --prompt hello --json | jq -r '.thread.id // .id'
  "$TB" thread spawn --project <home-id> --environment "$FX/Captains" --provider "$FAKE" --permission-mode full --pinned \
    --title verify-captain --prompt "You are a test Captain. Reply ready." --json | jq -r '.thread.id // .id'   # <captain-id>
  "$TB" thread show <captain-id> --json | jq -r .thread.status          # wait until idle: the first fake turn has finished
  D="$INST/data/thread-storage/<captain-id>"; mkdir -p "$D"; : > "$D/CAPTAIN.md"; : > "$D/CREW.md"; : > "$D/NOTES.md"   # the Drive new would create
  "$TB" plugin disable captain
  P="$INST/data/plugins/captain"; mkdir -p "$EV/captain-db-before"
  for f in data.db data.db-wal data.db-shm; do [ -e "$P/$f" ] && cp -p "$P/$f" "$EV/captain-db-before/"; done   # not data.db.bak-*
  NOW=$(($(date +%s)*1000))
  sqlite3 "$P/data.db" "INSERT INTO captains (thread_id, name, home_project_id, created_at) VALUES ('<captain-id>', 'verify-captain', '<home-id>', $NOW);
    INSERT INTO notices (key, first_seen, sent_at) VALUES ('title-suffix:<captain-id>', $NOW, $NOW);"
  "$TB" plugin enable captain
  "$TB" captain repo add <alpha-id> --captain <captain-id> --json      # Captain's own link path: state added, creates a Tasks project
  for n in Implement Review; do "$TB" tasks preset create --name $n --provider "$FAKE" --model acp-default --reasoning medium --permission full --json; done
  ```

  - These are the rows `new` writes (`captains`, its `title-suffix` notice, and `captain_repos` through `repo add`). Every thread Captain can message (the Captain and both fixture threads) runs on the fake provider. The `Implement` and `Review` presets exist only so adopt and `dispatch --dry-run` stop refusing `Tasks has no Implement preset`; `new` would create them on `claude-code`.
  - **What the stand-in lacks.** `thread spawn` cannot set `pluginMetadata.captain` or `originPluginId`, which only Captain's own spawn sets. So the stand-in gets no Captain instructions (`captain.md`, `CAPTAIN.md`, skills), its sidebar row shows no Captain icon, and Settle and Snooze stay enabled on it. Steps that need those stay marked.
  - **Restore.** Remove routines while the Captain is live, run `captain archive`, then `plugin disable captain`, delete `data.db-wal` and `data.db-shm`, copy the backed-up files back, and `plugin enable captain`. Delete the presets (`"$TB" tasks preset delete <id>`), the three projects, and `$FX`. Delete the Tasks projects `repo add` made through the RPC, since the CLI has none: find each id with `"$TB" tasks project list --json`, then `"$TB" plugin rpc call scott-tasks deleteProject --input-file <file holding {"projectId":"<id>","force":true}> --json`, which prints `{"ok":true,"deleted":true}`.

- **Every `"$TB" captain` call needs `--captain`.** `"$TB"` strips the `BB_*` environment, so the call has no calling thread. Without the flag Captain refuses with `not run from a bb thread; fix: run it in the Captain thread, or pass --captain <thread-id>`, and with a name or id that is not a live Captain, `no live Captain is "<value>"`. `new`, `ask resolve` and `ask show` take no `--captain`. The name works in place of the id (`--captain verify-captain`).

- **Refusals before any change (free).** `new` checks everything before it writes or spawns, so these are safe: `"$TB" captain new --name verify-refuse --json` refuses with `a Captain directs at least one repo`; `"$TB" captain new --name verify-refuse --repo verify-nope --json` refuses with `no bb project is "verify-nope"`; `"$TB" captain new --json` fails `missing required options: --name`. Each exits 1. Never add a valid `--repo` to a check: that starts a Captain.
- **CLI with no Captain (free).** `"$TB" captain status` refuses with `not run from a bb thread`. `"$TB" captain status --all --captain verify-nope`, `routine list`, `drive read` and `icon` with that `--captain` refuse with `no live Captain is "verify-nope"`. `"$TB" captain ask show a1 --json` and `"$TB" captain ask resolve a1 --answer Red --json` refuse with `no ask a1`.

## Gotchas

- `new` creates `~/Captains` in the server's home directory and points the test `Captains` project at it. The test server inherits the real `HOME`, and no CLI flag or plugin setting moves the folder, so a `new` Captain shares `~/Captains` with live's Captains. Never delete that folder. The Drive is not there: it is the Captain thread's own thread storage, `$INST/data/thread-storage/<captain-id>/`.
- The fake agent cannot be the Captain `new` starts, which is fixed to `claude-code`. It can be the seeded stand-in, and then answers, `tell`, routine tests and adopt wakes go to the fake provider for free. On a real Captain each of those is a paid turn.
- The stand-in has no `pluginMetadata.captain` and no `originPluginId`: no Captain instructions, no sidebar Captain icon, and Settle and Snooze stay enabled on its row. Do not report those as product gaps.
- Adopt and `dispatch` refuse with `Tasks has no Implement preset` (or `Review`) until those presets exist; `new` creates them on `claude-code`. A real dispatch creates `Captain <Role> · <n>` presets from the Crew models ladder, whose default rungs are `claude-code` and `codex`, so it is paid even on the stand-in.
- Adopting a thread wakes its new parent: bb sends the Captain `[bb system] @thread:<id> is now a child of this thread.`
- `Escape` on a settings page leaves Settings and returns Home. Press it only where a menu or dialog is open.
- `repo add`, `new` and adopt create Tasks projects and tasks in the test instance's Tasks, keyed from the bb project name (`verify-cap2-alpha` became `VERIFYCAP2`). Deleting the bb projects does not remove them, and `bb tasks project` has no delete; remove them with the `deleteProject` RPC as **Restore** describes.
- The banner mounts on every thread's composer but renders only on a live Captain's. A missing banner on a non-Captain thread is correct. `[data-testid="captain-needs-you"]` exists only while an item is queued; the empty `All clear` line sits in `section[aria-label="captain"]`.
- `Later` hides an item for an hour on the server, and a reload keeps it hidden. `captain status` still lists it. Open a fresh ask for each answer test.
- An active routine fires on schedule and costs a turn on a real Captain. A UI routine defaults to every weekday at 9:00, so pause or delete it in the same run. `--in`/`--at` one-shots stay armed until they run.
- Only the Captain's own thread, or a terminal call with `--captain`, manages routines. Crew and other threads are refused. <!-- unverified: from source; crew refusal not driven -->
- `New Captain directing <project>` renders only while bb's plugin list reports Captain running, and only on project group headers, which need two or more projects in view with grouping on. The plugin list is read once per mount, so reload Home after enabling Captain. The dialog's repo list leaves out the personal project and projects that hold a listed Captain.
- Two `Add rung` buttons exist on the settings page. Scope to a `… ladder` section before clicking.
- Collapsed Overview sections persist in this browser's localStorage under `captain:overview:<thread-id>`. Clear it, or toggle back, so later runs start expanded.
- The panel remembers Overview as its tab across reloads, so Overview showing after a reload does not prove the default. Select Info first, then hide and show the panel.
- The sidebar lead holds an empty `data-captain-icon="loading"` box while the icon loads, and shows the globe while Captain is disabled or for an archived Captain. <!-- unverified: needs a Captain started by `new` -->
- Captain threads are pinned and titled with the name alone. gtd-sidebar's namer may still rewrite a fixture thread's title, so wait for the title before asserting. <!-- unverified: needs a Captain started by `new`; the stand-in's title and pin come from `thread spawn` -->
- `"$TB" project delete <home-id>` also deletes every Captain thread in it, archived ones included: `thread show <captain-id>` then returns `thread_not_found`, and the Drive folder under thread storage goes with it.
- Restore Captain's database only while the plugin is disabled, and delete any `data.db-wal` and `data.db-shm` the backup lacks, so a newer write-ahead log is not applied over the restored file. Disabling Captain checkpoints its log, so the backup is usually `data.db` alone.
